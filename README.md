## 2. SLO ба Error Budget

| Сценарио         | SLI (Юуг хэмжих)               | Босго                         | Цонх / Нөхцөл            |
| :--------------- | :----------------------------- | :---------------------------- | :----------------------- |
| **Performance**  | `/cart/add` latency            | $p(95) < 10\text{ms}$         | 20 VU, 1 мин             |
| **Performance**  | `/report` latency              | $p(95) < 450\text{ms}$        | 20 VU, 1 мин             |
| **Reliability**  | `/pay` error rate              | $\text{rate} < 0.08$ ($8\%$)  | 20 VU, 1 мин             |
| **Availability** | Нийт хүсэлтийн амжилт (checks) | $\text{rate} > 0.90$ ($90\%$) | 2 мин, 10с зогсолт орсон |

### Босго сонгосон үндэслэл

- `/pay` endpoint дээр сервер зориудаар ойролцоогоор 5%-ийн алдаа үүсгэдэг тул санамсаргүй хэлбэлзэл болон нэмэлт алдааны зайг тооцож 8%-ийн error rate-ийн босгыг сонгосон.
- Localhost орчинд `/cart/add` endpoint нь туршилтаар ойролцоогоор 1–2ms-ийн response time үзүүлж байсан ба лабораторын удирдамжин дээр ихэвчлэн 1-5 мс-д хариулдаг гэж бичсэн байсан тул p(95) < 10ms босгыг сонгосон.
- `/report` endpoint нь 200–400ms-ийн санамсаргүй delay-тэй тул хэвийн хэлбэлзэлд бага зэрэг зай үлдээж `p(95) < 450ms` босгыг сонгосон.

### Availability Error Budget

Availability SLO = 90% тул error budget = 10%.

2 минутын цонхонд:

$$
120\text{с} \times 10\% = 12\text{с}
$$

Иймээс **time-based error budget = 12 секундийн downtime**.

## 4. Дүгнэлт ба Chaos туршилтын ажиглалт

Энэ лабораторийн ажлаар чанарын сценариогоо SLO болгон тодорхойлж, дараа нь k6 дээр threshold хэлбэрээр хэрэгжүүлж үзлээ. Сценариогоос threshold сонгох үед хамгийн хэцүү зүйл нь шууд дурын тоо сонгох биш, тухайн endpoint-ийн бодит ажиллагаатай нь тохируулах байсан. Жишээлбэл, `/cart/add` нь localhost дээр ойролцоогоор 1.43ms-д хариулсан ба лабораторын удирдамжин дээр ихэвчлэн 1-5 мс-д хариулдаг гэж бичсэн байсан тул байсан тул `p(95)<10ms` босго тавьсан. Харин `/report` нь зориудаар 200–400ms delay-тэй учраас `p(95)<450ms` гэж тохируулсан. `/pay` endpoint-ийн 5%-ийн зориудаар үүсгэсэн алдааг харгалзан error rate-ийн босгыг `8%` болгосон.
Chaos туршилтаар серверийг 10 секунд зогсооход хүсэлтүүд `Connection Refused` болж, checks rate `83.21%` хүртэл буурсан тул 90%-ийн Availability SLO хангагдаагүй. Мөн энэ үед `/pay` error rate `19.42%` болсон нь серверийн нэг outage хэд хэдэн хэмжүүрт зэрэг нөлөөлж болохыг харуулсан. 90%-ийн Availability SLO-ийн 2 минутын time-based error budget нь 12 секунд боловч k6-ийн checks нь хугацаагаар биш хүсэлтээр тооцогддог учраас 10 секундын outage нь олон request-ийг зэрэг амжилтгүй болгож, availability хувийг илүү ихээр бууруулж байгааг ажиглалаа. Зориуд FAIL туршилтаар `/report`-ийн threshold-ийг `p(95)<100ms` болгож өөрчлөхөд бодит p95 нь `392.01ms` гарч, k6 `exit code 99` өгсөн. Ингэснээр threshold-ийг зөв тохируулахаас гадна босго зөрчигдсөн үед k6 тестийг амжилтгүй болгож чаддагийг шалгаж үзлээ.
