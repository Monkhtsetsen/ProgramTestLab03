## 2. SLO ба Error Budget

| Сценарио         | SLI (Юуг хэмжих)               | Босго                         | Цонх / Нөхцөл            |
| :--------------- | :----------------------------- | :---------------------------- | :----------------------- |
| **Performance**  | `/cart/add` latency            | $p(95) < 10\text{ms}$         | 20 VU, 1 мин             |
| **Performance**  | `/report` latency              | $p(95) < 450\text{ms}$        | 20 VU, 1 мин             |
| **Reliability**  | `/pay` error rate              | $\text{rate} < 0.08$ ($8\%$)  | 20 VU, 1 мин             |
| **Availability** | Нийт хүсэлтийн амжилт (checks) | $\text{rate} > 0.90$ ($90\%$) | 2 мин, 10с зогсолт орсон |

### Босго сонгосон үндэслэл

- `/pay` endpoint дээр сервер зориудаар ойролцоогоор 5%-ийн алдаа үүсгэдэг тул санамсаргүй хэлбэлзэл болон нэмэлт алдааны зайг тооцож 8%-ийн error rate-ийн босгыг сонгосон.
- Localhost орчинд `/cart/add` endpoint нь туршилтаар ойролцоогоор 1–2ms-ийн response time үзүүлж байсан ба лабораторын удирдамжин дээр ихэвчлэн 1-5 мс-д хариулдаг гэж бичсэн байсан тул p(95) < 10ms босгыг сонгосон.
- `/report` endpoint нь 200–400ms-ийн санамсаргүй delay-тэй тул энэ хүлээлгийн хугацаанд бага зэрэг нөөц үлдээж p(95) < 450ms босгыг сонгосон.

### Availability Error Budget

Availability SLO = 90% тул error budget = 10%.

2 минутын цонхонд:

$$
120\text{с} \times 10\% = 12\text{с}
$$

Иймээс **time-based error budget = 12 секундийн downtime**.

## 5. Дүгнэлт ба Chaos туршилтын ажиглалт

Энэ лабораторийн ажлаар чанарын сценариогоо SLO болгон тодорхойлж, дараа нь k6 дээр threshold хэлбэрээр хэрэгжүүлж үзлээ. Сценариогоос threshold сонгох үед хамгийн хэцүү зүйл нь шууд дурын тоо сонгох биш, тухайн endpoint-ийн бодит ажиллагаатай нь тохируулах байсан. Жишээлбэл, `/cart/add` нь localhost дээр `1.38ms`-ийн p95 latency үзүүлсэн бөгөөд лабораторын удирдамжид ихэвчлэн 1–5 мс-д хариулдаг гэж бичсэн байсан тул `p(95)<10ms` босго тавьсан. Харин `/report` нь зориудаар 200–400ms delay-тэй учраас `p(95)<450ms` гэж тохируулсан. `/pay` endpoint-ийн ойролцоогоор 5%-ийн зориудаар үүсгэсэн алдааг харгалзан error rate-ийн босгыг `8%` болгосон.

Chaos туршилтаар серверийг 10 секунд зогсооход олон хүсэлт амжилтгүй болж, checks rate `82.14%` хүртэл буурсан тул 90%-ийн Availability SLO хангагдаагүй. Мөн энэ үед `/pay` error rate `20.38%` болсон нь серверийн outage нь хэд хэдэн хэмжүүрт зэрэг нөлөөлж болохыг харуулсан. 90%-ийн Availability SLO-ийн 2 минутын time-based error budget нь 12 секунд боловч k6-ийн checks нь хугацаагаар биш хүсэлтээр тооцогддог учраас 10 секундын outage нь олон request-ийг зэрэг амжилтгүй болгож, availability хувийг илүү ихээр бууруулж байгааг ажиглалаа. Харин Chaos туршилтын үед `/cart/add`-ийн p95 `2.39ms`, `/report`-ийн p95 `390.48ms` байсан нь тус хоёр endpoint-ийн performance threshold-үүдийг хангаж байгааг харуулсан. Зориуд FAIL туршилтаар `/report`-ийн threshold-ийг `p(95)<100ms` болгож өөрчлөхөд бодит p95 нь `388.61ms` гарч, k6 `exit code 99` өгсөн. Ингэснээр threshold-ийг зөв тохируулахаас гадна босго зөрчигдсөн үед k6 тестийг амжилтгүй болгож чаддагийг шалгаж үзлээ.

## 6. AI-ийн бичсэн чанарын сценариудын дүгнэлт

### Давуу тал

AI-ийн бичсэн сценарионууд нь өдөөгч, орчин, хариу үйлдэл болон хэмжүүрийг тодорхой бичсэнээрээ ойлгомжтой байсан. Мөн endpoint бүрийн зорилго болон хэмжих үзүүлэлтийг тодорхой тусгасан нь миний бичсэн сценариотой харьцуулахад илүү ойлгомжтой байсан.

### Дутагдал

#### 1. Баталгаагүй тоон босгууд

AI-ийн санал болгосон `/cart/add`-ийн 500 req/s, p95 < 50 мс, p99 < 100 мс зэрэг босгууд нь `server.js`-ийн бодит хэрэгжилт дээр үндэслээгүй. Иймээс шууд ашиглахад бодитой эсэх нь баталгаагүй.

#### 2. `/pay` дээрх байхгүй механизмууд

`/pay` endpoint дээр idempotency key, exponential backoff болон автоматаар retry хийх механизм байгаа мэтээр бичсэн боловч миний `server.js` дээр ийм логик байхгүй.

#### 3. `/report` дээрх баталгаажаагүй нөхцөлүүд

`/report` дээр 20 хэрэглэгч зэрэг хүсэлт гаргах болон бусад endpoint-ийг блоклохгүй гэсэн нөхцөлүүдийг код шууд баталгаажуулаагүй.
